# MCU Firmware 開發與 GitHub Copilot 整合實驗記錄

## 緣起：尋找 MCU 開發的 AI 助手

這幾日雙十假期，花了半天做了一個嘗試。一直以來都用 Keil IDE 在做 Nuvoton MCU firmware 的開發，當 GitHub Copilot 開始可以在電腦端協助開發 Python、JavaScript 網頁前端的時候，我就持續嘗試怎樣可以讓這個好處來協助 MCU firmware 的開發。

**都是程式語言，語法都一樣？為何那麼困難整合？**

一直到最近 GitHub Spec-Kit 推出，還有 GitHub Copilot 更新到可以支援客製化的 prompts，AI 撰寫 MCU firmware 這件事情開始讓我覺得越來越可行了。

而且 VSCode IDE 整合 ARM Studio 開發的套件也成熟，最棒的是 Nuvoton 推出 Cortex-M VSCode 擴充套件，讓 Nuvoton MCU BSP 更容易在 VSCode IDE 上面整合。因為這樣我就可以很容易搭配 GitHub Copilot 這樣的 AI 協助開發 firmware。

## 環境轉換：從 Keil 到 VSCode

### 為什麼選擇 VSCode？

1. **原生 Copilot 支援**：VSCode 對 GitHub Copilot 的整合最完善
2. **開放生態系**：豐富的擴充套件和社群支援
3. **ARM Studio 套件成熟**：ARM 官方的 VSCode 開發套件已經相當穩定
4. **Nuvoton 官方支援**：Cortex-M VSCode 擴充套件讓 BSP 整合變得簡單

### 環境配置工具鏈

- **VSCode**：主要開發環境
- **ARM Studio Extension**：ARM 開發工具整合
- **Nuvoton Cortex-M Extension**：Nuvoton 特定 MCU 支援
- **GitHub Copilot**：AI 程式碼助手

## 四個關鍵發現

以下是我這半天發現幾件有幫助的地方：

### 1. 環境配置的自動化救星

**過去的痛點：**

以前當 Keil 配置錯誤，根本不知怎麼辦，只能一直套用原廠給的框架。環境設定是最沒有產出的工作，但卻非常耗時。而且工具每隔幾年都會更新，狀況又會不一樣。

**現在的解決方案：**

當配置出問題，只需要透過 Copilot 問他為何？並請他直接將環境設置好，省去很多時間。

這讓我可以：
- 快速診斷配置問題
- 自動修正設定檔
- 減少重複性的環境設定工作
- 專注於實際的功能開發

### 2. 客製化指令與 AGENTS.md 的威力

**核心概念：先定義限制，再開始創作**

我發現最重要的是在專案開始前，先建立一個完整的 `AGENTS.md` 或客製化指令檔案，把專案的關鍵資訊寫清楚：

#### 硬體限制與資源配置
- MCU 型號與規格
- 可用的記憶體資源（Flash、RAM）
- 時脈頻率與功耗限制

#### 電路板 I/O 設置
- GPIO 接腳定義（例如：PA0 接綠色 LED，高電位驅動）
- 串列週邊配置（UART、I2C、SPI 使用的接腳與速率）
- 中斷優先級設定

#### 程式撰寫規範
- 變數命名規則（例如：使用 snake_case 或 camelCase）
- 是否採用物件導向寫法
- 優先考量：效率還是 code size？
- 註解風格與文件規範

#### 實踐步驟

1. **撰寫詳細的專案限制文件**
2. **請 Copilot 將文件轉換成更有效率的 prompts**
3. **讓 Copilot 每次產生 code 都遵守這些規則**

**效果：**

這樣產生的 code 就不會出現「幻想」——例如使用了不存在的硬體資源，或是調用了未定義的週邊。

### 3. 由下而上的架構規劃

**重要發現：先打通底層，再建構系統**

在規劃整體專案前，**一定要先把低層的周邊驅動先打通**。

#### 建議的開發順序

1. **底層驅動層**：
   - GPIO 驅動
   - 串列通訊驅動（UART、SPI、I2C）
   - Timer 驅動
   - 中斷處理機制

2. **硬體抽象層**：
   - 將驅動封裝成物件或函式介面
   - 提供統一的 API
   - 隱藏硬體細節

3. **應用層**：
   - 系統流程處理
   - 商業邏輯實作
   - 使用者介面

**好處：**

當建構系統時，只需要處理系統流程，不用再擔心底層細節。這種架構讓 AI 更容易理解專案結構，產生正確的程式碼。

### 4. Debug 的重要性：printf 與 GDB

**沒有 debug printf port，真的很難抓問題！**

#### Debug 工具的必要性

雖然有 GDB 可以用，但如果 code 不是自己寫的，根本不知道斷點要放在哪裡。

**建議配置：**

1. **預留 UART Debug Port**：
   - 專門用於輸出除錯訊息
   - 不與正常通訊共用
   - 可以隨時加入 printf 追蹤

2. **結構化的 Debug 訊息**：
   ```c
   // 範例：使用階層式 debug 訊息
   #ifdef DEBUG
   #define DBG_PRINT(level, msg, ...) \
       printf("[%s] " msg "\r\n", level, ##__VA_ARGS__)
   #else
   #define DBG_PRINT(level, msg, ...)
   #endif
   
   // 使用方式
   DBG_PRINT("INFO", "System initialized");
   DBG_PRINT("ERROR", "Failed to init I2C: %d", error_code);
   ```

3. **配合 GDB 使用**：
   - AI 產生的程式碼可以加上詳細註解
   - 說明關鍵邏輯點的用途
   - 方便設定有意義的中斷點

## 深度思考：AI 與人類的協作邊界

### AI 越來越進步，但仍有界限

**氛圍編碼**（Ambient Coding）越來越進步，但有最後一哩路是永遠也取代不了的：

#### AI 的限制

1. **硬體驅動的特殊性**：
   - 每個 MCU 的週邊設定都不同
   - 暫時還沒有統一化的標準
   - 需要深入理解晶片手冊

2. **實際世界的不確定性**：
   - 往實際世界連結的部分是 AI 無法掌控的狀況
   - 電氣特性、時序要求、雜訊干擾
   - 這些都需要實際量測和除錯

#### 人類的不可取代性

- **硬體知識**：理解電路原理和訊號特性
- **實務經驗**：知道常見的問題和陷阱
- **整合能力**：將軟體與硬體結合
- **除錯直覺**：從現象推斷問題根源

### 最佳組合：人類 + AI 共同創作

**AI 可以協助：**
- 快速產生樣板程式碼
- 自動化環境配置
- 提供程式建議和優化
- 加速文件撰寫

**人類需要負責：**
- 定義系統架構
- 設定硬體參數
- 驗證功能正確性
- 處理特殊狀況

這不是替代關係，而是**增強關係**。AI 處理重複性和規則性的工作，人類專注於需要創意和判斷的部分。

## 結語

這次實驗讓我看到了 MCU firmware 開發的新可能性。雖然還有很多細節需要調整，但方向是對的。

**關鍵心得：**
- **環境配置自動化**讓我們不再被工具鏈困擾
- **客製化指令**讓 AI 理解專案限制，避免產生無效程式碼
- **分層架構**讓開發更有條理，也讓 AI 更容易協助
- **人機協作**才是最佳解，而非單純的替代
